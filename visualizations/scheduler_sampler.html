Samplers and schedulers in diffusion language models

Schedulers

A masked diffusion language model is trained to repair text in which random tokens have been replaced by [MASK]. The scheduler is the rule for how much text is masked at each point of a continuous “time” t between 0 (clean text) and 1 (nothing but masks). Its value, α(t), is the probability that a token has survived.

Generation runs the clock backwards: start at t = 1 with an empty canvas, and step towards t = 0, revealing a few tokens at each step. The scheduler is what tells the sampler how many.

Two things to try. Compare Linear and Cosine at the same t: one corrupts text at a constant rate, the other front-loads it. Then pull s up to t and watch the reveal probability collapse. A tiny time step reveals almost nothing, which is why the number of sampling steps matters.

The one line the sampler needs

Of everything a scheduler offers, sampling uses a single quantity, reverse_mask_prob(s, t) for s < t. Its formula looks arbitrary until you notice that masking is absorbing: a token that is masked never becomes unmasked as time increases. So a token masked at the earlier time s was necessarily also masked at t, and the conditional probability is just a ratio of marginals:

P(masked at s | masked at t) = P(masked at s) / P(masked at t) = (1 − α(s)) / (1 − α(t))

One minus this is the chance that a masked token gets revealed in that step. That is the number handed to the next stage of the sampler.

Why there is also a derivative

Every scheduler implements two hooks, _value and _derivative, and the sampler never calls the second one. It exists for training. When the model is trained to fill in masked tokens, the loss at a time t is weighted by w(t) = −α′(t) / (1 − α(t)), which is why weight() needs the slope. In other words, the scheduler is shared between the two halves of the system: training uses its slope to decide how much each noise level counts, and sampling uses its value to decide how fast to denoise.

The kappa schedulers next to it have the same shape but belong to a different model family (edit flows), so the samplers ignore them.

Samplers

The scheduler says how much to reveal; the sampler does the revealing. Both samplers in this codebase share one skeleton: put the prompt and a run of [MASK] tokens on a canvas, then repeat predict every masked position, keep a few predictions, write them into the canvas until no masks are left. What differs is what the model is allowed to see, and therefore what can be cached.

How many tokens per step

The scheduler gives a probability per step, but the sampler needs whole numbers per batch row. get_num_transfer_tokens does the conversion, and two of its design choices are not visible in the numbers alone.

  • It is a recurrence, not a formula. Step j reveals round(remaining × pj), and remaining depends on the rounding of every earlier step, so the steps cannot be computed independently. The probabilities can, so they come from one scheduler call and only the cheap rounding loop stays sequential.
  • Empty steps are dropped. These models are not conditioned on the diffusion time, so a step that reveals nothing would be a full forward pass over an unchanged input. The function packs each row's non-empty steps to the left and trims the rest, which also lets rows with few masks finish early.

With stochastic_transfer the rounding is replaced by a Binomial draw, so the counts themselves, not only the chosen tokens, become random.

Which tokens: a batched top-k

Once we know that row b should reveal k[b] tokens this step, we have to choose which: the k[b] masked positions the model is most confident about. The obvious code loops over rows and calls torch.topk with a different k each time, which launches one tiny kernel per row and, because k[b] lives on the GPU, waits for the device once per row.

topk_transfer_mask does it with a single call. It takes the top k_max of every row, where k_max is the largest k in the batch, and then masks out the surplus in rows that wanted fewer. Two details matter. k_max is passed in as a plain Python integer, computed once per block, so the function itself never has to wait on the GPU. And positions with confidence −inf (not masked, or outside the current block) are never selected, so a row with fewer candidates than k simply selects fewer.

Greedy or sampled: Gumbel noise

The model outputs a score for every vocabulary entry at every masked position, and something has to turn those scores into a proposed token. At temperature 0 that is a plain argmax. Otherwise the sampler adds Gumbel noise to the logits first, scaled by the temperature, and takes the argmax of the result. The useful fact is that this is exactly sampling from softmax(logits / T), so a categorical draw is reduced to an argmax, which is cheap and batches well.

Note what the noise does not touch. The proposed token comes from the noisy logits, but the confidence used to rank positions is the probability of that token under the clean logits. Randomness therefore changes what is proposed without changing how sure the model is about it. The noise is generated in float64: in the masked-diffusion setting, lower precision improves perplexity but hurts generation quality (arXiv:2409.02908).

MDLM: read everything, commit a block

MDLM decoding treats the model as a plain bidirectional denoiser. It was trained on randomly masked text and knows nothing about blocks; blocks exist only in the sampler, as a restriction on which positions may be committed. Each step the model predicts every masked position, the confidence of those predictions ranks them, and the top k inside the current block are kept. The others are not stored anywhere. They stay masked and are predicted again next step, which is all that “remasking” means here.

Why restrict to a block at all? In LLaDA's experiments, letting confidence pick from the whole canvas tends to commit the padding and end-of-sequence positions at the far end first, because the model is very sure about them, and the answer gets cut short. Decoding blocks left to right avoids that while still filling each block in parallel.

Two consequences show up in the counters. First, the forward pass can never shrink. Attention is bidirectional, so committing a single token changes the hidden state of every position, the prompt included, and no key or value can be reused. Every step costs B × T tokens. Second, everything after the forward pass only needs the current block. The noise, argmax and softmax over the vocabulary can run on a slice of the columns instead of the whole canvas, and that is where an implementation can save work.

BD3LM: block-causal, so the past can be cached

Block diffusion changes the model, not just the sampler. It is trained with a block-causal attention mask: a token sees its own block and all earlier blocks, never later ones. Two things follow. The canvas can grow one block at a time and stop early on EOS. And a finished block's keys and values can never change again, so they can live in a KV cache, which is exactly what MDLM cannot have.

The sampler manages that cache with three operations: prefill the prompt once, roll back after every denoising step, and extend once per finished block. The rollback is the subtle one. Hugging Face style caches are updated in place by any forward pass, even one called with use_cache=False, so a denoising step would otherwise leave its tentative block keys and values behind. The simple fix is to deep-copy the whole cache before every step; cropping it back afterwards does the same job without the copy.

The counters compare against the straightforward implementation, which re-encodes the entire prefix at the start of every block and deep-copies the cache at every step. Re-encoding makes total prefill work grow quadratically with the number of blocks instead of linearly; the copies multiply memory traffic by the prefix length.
